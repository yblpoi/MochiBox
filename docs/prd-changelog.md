## 修订记录

- **v0.3.4 修订存档**：**P0-09 契约修正**：`\d+` 未锚定会整句漏译，改为 `^\d+$`；补"跳过项不写缓存"与两条并列断言。P1-10 补缓存纯度要求（需求口径）。§4.2 补语言只读断言。**需 QA 对 P0-09 复验**
- **同日内部修订**（不升版号，避免跨文档版本震荡）：§5.1 新增"跳过判定的作用对象"——正则作用于剥码后的 `text` 而非 `raw`；补 `\C[2]350` / `\C[2]10秒後` 两条边界。经核实 V0.1 实现本已符合（逐字符 `allDigits` 判定 + 入队前 skip），本次为**文档缺口补全**，非线上缺陷
- **同日内部修订（续）**：P0-09 / P1-10 的断言由两条补为**三条**，新增第 (3) 条锁"**假译文**"——跳过项不得落 `hit`/`translated`、非 `passthrough` 时 `translatedRaw` 不得等于 `raw`；并明确 `passthrough` 是唯一例外（须显式标记，不得静默写缓存冒充译文）。原两条只锁了计费与脏数据，**假译文面此前无任何断言**
- **同日内部修订（三）**：第 (3) 条判据由"比内容"改为"**问来源**"——原写法 `translatedRaw == raw` 会把 `OK`/`BGM`/`HP` 等**恒等翻译**判成假译文（假阳性），并可能诱导实现方把正确行为改坏；新增**禁止条款**明确不得以内容相等作判据。`passthrough` 例外改为仅作用于 `status`。(2) 补"内存与落盘判据同源"。P1-10 的 (c) 同步改为来源校验
- **同日内部修订（四）**：补两条**阳性断言**（防"沉默实现全绿"）——P0-07 增"`uninstall()` 后重新注入仍能采集且 hook 不叠加"；§5.4 增"段数一致时按原段位重组、`code` 段数量位置不变且必须写缓存"。原有断言以"不该发生"为主，一个"什么都不做"的实现可通过全部阴性断言
- **同日内部修订（五）**：①§5.5 `retryable` 明确"由本次失败性质决定、非 code 静态属性"，并禁止简化成"按 code 查表"（`bad_response` 在 5xx 时 `true`、4xx/非 JSON 时 `false`）；②§3.2 C 组把成功样本（200 → 无 `ErrorInfo` + 写缓存）与失败样本（**4 个 code**）分开断言，禁止凑"六个 code"、禁止要求 200 返回错误码（假阳性）
- **同日内部修订（六）**：①`circuit_open` 定为 `retryable = false`（立即重试必失败），但 UI 须显示"约 N 秒后自动重试"、不得呈现终局失败（P0-13 同步加"熔断期不得提供立即重试入口"）；②§3.1 增"原因 ≠ 结果"枚举判据——按原因分类（code/内容）不得用于推断结果属性（retryable/是否脏/是否展示），4 个实例已记录
- **同日内部修订（七）**：①P0-13 增熔断期可验断言（`code=circuit_open` + **`retryable === false`** + 倒计时文案 + 无"立即重试"入口），防后续被改回 true；②§3.1 增"定义贴在列表末尾 / 新增成员必须回引定义"——针对"枚举补全时的语义漂移"（4 个假阳性实例的共同成因）
- **同日内部修订（八）**：§A.1 规则 12 的 `*.pck` **排除 `Scene.pck`**。原写法下 `Scene.pck`（规则 13 Siglus 的精确特征）匹配 `*.pck` 通配，按"12 先于 13"被判成 `godot` —— **实现照字面执行无错，是需求本身的包含关系缺陷**。并新增"表内包含关系原则：精确名优先于通配，且不得靠行序表达"
- **同日内部修订（九）｜缓存键空间变更**：§5.1 `key` 公式改为 `normalizeForKey(join(...))` —— 原公式未引用同节定义的 `normalizeForKey`（**死定义**），且 §3.2 B 组断言"NFKC/空白归一"，**PRD 内部自相矛盾**。同时写死三件事：①归一作用于 **join 之后整串**（非逐段归一，段内首尾空白处理不同）；②空白折叠改用**显式 5 码位白名单**，禁止 `.whitespaces`/`\s` 等平台相关集合（跨平台覆盖不一致 → 同一句算出不同键；若误用含 C0 控制字符的集合会吃掉 `U+001F` 毁掉分段）；③`U+001F` 不参与任何归一。**影响**：缓存键空间变化 → 旧缓存不可复用（本轮无线上缓存，零迁移成本）
- **同日内部修订（十）**：§5.1 归一条款改写为**三个不变量**（①显式折叠空白 ②不得丢弃任何非空白字符 ③`U+001F` 个数与**位置序列**均不变），三条必须同时成立。第 ③ 条强调"位置序列"而非仅"个数"。并附**规范依据**（`U+001F` 属 Cc；`.whitespaces` = Zs + U+0009，不含 Cc）澄清禁令理由，避免被误读为"`whitespaces` 会吃掉分隔符"。**注：该版第 ③ 条的"位置序列"表述有误，见修订（十一）。**※ **同日内部修订（十一）**：§5.1 不变量 3 由"个数**与位置序列**均不变"改为 **3a 个数 + 3b 段内容**。**原写法会在正确实现上失败**：折叠空白必然改变后续字符下标（`["甲  ", "乙"]` 中 `␟` 下标 3 → 归一后 2），故"位置/下标不变"不可作为断言；并删除原举例 `A␟B` 与 `A B␟`（该例不成立，是为支撑错误断言而编的）。同时按主理人/架构师要求，三条不变量**各自补"一进一出"例子**，无例子视为未定义
- **同日内部修订（十二）**：①**P0-08 去重口径**由"同帧同内容 + 同 surface"改为"**同一显示窗口（默认 800ms）+ 同 surface + 同 `raw`**"——原写"同帧"会误导实现按帧号分桶，而**跨帧重绘压不住**（行数风暴会重现）；同时明确**行身份按 `raw` 不按 `key`**（否则 `350` 与 `\C[2]350` 签名相同、后者被静默吞掉）。②§5.2 `occurrences` 由"同 key 观测次数"改为"**同 `surface` + `raw` 观测次数**"（`350` 与 `\C[2]350` 是两行同一个 key，按 key 计数会互相污染）
- **同日内部修订（十三）｜模型裁定**：确定采用**多行模型**（同一身份每次出现新增一行），并据此补齐两处：①`occurrences` 明确为"**截至本行的累计次数**"（第 n 行为 n，**不回填已渲染行**）；②P0-08 与 AC3.1 增**阳性断言"窗口外必须新增行、禁止永久去重"**——原文只有"窗口内去重"，一个"每句只 emit 一次"的实现同样能满足，属 R1-③ 阳性对照缺失
- **同日内部修订（十四）｜收口**：QA 用可控时钟探针复核（1600ms 后再现 → 累计 2；连续重绘 8×400ms → 仍为 2），确认**窗口模型成立、非永久去重**，`captured=4` 由 BUG-8 的 `mapKey` 碰撞解释。据此细化三处：①**去重窗口 = "距上次同身份绘制 > 800ms"（滑动续期，非固定分桶）**，故持续可见只出 1 行；②AC3.1 拆为 **a｜离屏后再次出现（各成一行，occurrences 1/2/3）** 与 **b｜持续可见（1 行、occurrences 不增）**，并注明后者判重复行/判缺陷均为误判；③`occurrences` 明确为"**行序号**"（持续可见的重复重绘不计入）。另增断言写法要求：**不得用事件总数作判据**（总数随重绘节奏变），应断言"出现过哪些 `(surface, raw)`"
- **同日内部修订（十五）**：AC3.1 由两种情形扩为**三种**，并按架构师意见**去掉"离屏"这一肉眼词**（不可构造用例），判定基准只保留"**距上次绘制的间隔**"。新增 **c｜续期判别**（连续重绘 8×400ms 后 +100ms 再绘 → 仍 1 行）——**a 与 b 各自都能被"续期"与"不续期"两种实现同时通过，只有 c 能分辨**。另把可控时钟探针数据作为**实测依据**留在 AC3.1 下，使"非永久去重"与"续期抑制"两个结论可复核
- **同日内部修订（十六）**：①AC3.1 扩到**五种情形**，新增 **d｜多身份交错**（区分"全局单一时间戳"缺陷：A/B 交错各 1 行；全局实现会误吞 B）与 **e｜同 `raw` 不同 `surface`**（区分"签名漏 `surface`"缺陷：两行、共享同一 `cacheKey`）；②新增**边界取值要求**（禁测 800ms 精确边界，窗内 ≤400ms、窗外 ≥1600ms，防 flaky）；③P0-08 增"**间隔必须用单调时钟 `performance.now()`，不得用 `Date.now()`**"——墙钟校正会产生负间隔（卡住）或巨间隔（暴增），两者都不报错；④`occurrences` 明确**基于当前保留行**、淘汰后可重回 1、**不得跨淘汰/跨会话持久计数**（主理人裁定：用户无法核对的数字即假数字；且该 map 无界增长，正是环形缓冲要防的东西）
- **同日内部修订（十七）**：P0-08 补**生命周期语义**——`clear` 只清视图、不清 Agent 侧去重状态，故清空后 **800ms 内重绘不新增行、>800ms 后正常新增**，并注明"**这是预期行为，不是缺陷**"。补此项的原因：该行为会被 QA 稳定误报为"清空后文本流不动"，属"契约缺一句预期"而非实现缺陷。其余生命周期事件（暂停/恢复、`enabled` 开关、重连、页面重载、5000 行淘汰）**均不产生可见差异**，故不写入契约（对照表见任务 #6 第 9 项）
- **同日内部修订（十八）**：①**P0-08 增宿主侧行身份断言**——同帧内 `350` 与 `\C[2]350` 同时绘制必须 **`rows.count == 2`** 且共享同一 `cacheKey`（不重复计费）；只按 `cacheKey` 认行的实现会并成 1 行（对应 BUG-10：页面侧已按 `surface+raw`，宿主侧仍按 `cacheKey`）。②**§5.4 增"一条译文扇出到所有共享 `cacheKey` 的行"**——只填首行会让另一行永久 `pending`，违反 AC2.2b 且现场像"后端慢"；重译/清缓存同理。③**P0-09 增判据边界对照**——`"3 5 0"` **不跳过**（`numeric` 不剥内部空白）vs `"! !"` **跳过且 reason=punctuation**（`punctuation` 先移除 5 个折叠码位）；成对记录以防"顺手统一"
- **同日内部修订（十九）**：§5.4 扇出语义补**失败路径**——401 / 超时 / 熔断 / `passthrough` 同样必须落到**所有**共享 `cacheKey` 的行（状态转 `error` 或 `passthrough`）。只扇出成功的实现在失败时留下一行 `pending` 直到超时，**症状与"只填首行"完全相同**且更易被误判为"后端慢"。断言：401 场景下两行**都**不得停留 `pending`
- **同日内部修订（二十）｜修正失效断言**：P0-08 的宿主侧断言拆成**两个样本**——样本 A（`350` + `\C[2]350`，均 `skipped`、零请求）只断言 `rows == 2`；样本 B（`こんにちは` + `\C[2]こんにちは`，可翻译、同 `cacheKey`）断言 `rows == 2` **且** `newTranslations == 1` + 双行离开 `pending`。**原写法在样本 A 上断言"不重复计费"属恒真**（A 一条请求都不发），"两行各发一次请求"的过度修复也测不出；§5.4 的扇出示例同步换成 `こんにちは`，并明写"不得用 `350` 验扇出"
- **同日内部修订（二十一）**：①P0-08 的 B 组加**断言边界**——只验行数/请求数/状态收敛，**不验两行各自的转义码形态**（同 `mapKey` 不同 `raw` 共享一格译文，渲染可能丢码/加色，属 **BUG-11 已知未修**；B 组若断言控制码形态必红，且属"已知缺陷被新断言撞上"而非实现退步）。②记录**行唯一 id 的错误后果**更正为：**`ForEach` 行复用串位、选中项跳走、滚动定位错乱**（原写"扇出更新错行"有误——扇出是按 `cacheKey` 遍历全部行，不按 id；用 id 扇出才是扇出逻辑错）。实现要求：**新增行时生成 id，更新既有行不得换 id**
- **同日内部修订（二十二）｜失败扇出补"整体失败"形态（需求缺陷，工程修复 BUG-10 时发现）**：§5.4 原写"只扇出成功的实现，在失败时会留下一行 `pending`，**症状与'只填首行'完全相同**"——该描述**只覆盖部分失败**。**整体失败（401/429/超时/熔断）时批次 `items` 为空**，只遍历 `items` 才落状态的实现**一行都不会更新**，后果是"**所有在飞行行停在 `pending`**"，比"一行 `pending`"更重、症状也不同（整个文本流冻住），原表述把两种后果混成一句会**系统性漏掉更常见的一类**。已拆成 (a)/(b) 两形态 + (i)/(ii) 两条断言。同一修订：修文档元信息表被裸换行切断（**`版本` 行末尾缺闭合竖线**，导致其后的 `交付范围` 行脱离表体、渲染成孤行文字）
