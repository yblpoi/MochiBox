# 手工验收记录（运行时事实）

| 项 | 内容 |
|---|---|
| 文档性质 | **只记录"某次运行的事实"**：谁、在什么环境、点了什么、看到什么 |
| 不包含 | 断言规则（见 `docs/acceptance-assertion-rules.md`）、需求口径（见 `docs/prd.md`）、设计约束（见 `docs/architecture.md`） |
| 填写人 | 实际执行 GUI 实测的人（QA / 工程 / PM 均可，但必须**真的执行过**） |
| 状态 | 本文档尚无任何实测记录（§1 全部"未验证"） |

---

## 0 状态三态（每个需求条目都必须处于其中一种）

| 状态 | 含义 | 升级条件 |
|---|---|---|
| **未验证** | 没有任何记录 | 默认值。**任何"能用 / 正常 / 已修复"的说法，在该项处于"未验证"时均不成立** |
| **已验证** | 有记录，且观察到结果符合 PRD | **必须**在 §1 填记录号（如 `R-003`），无记录不得标此状态 |
| **验证失败** | 有记录，且观察到结果不符 | **必须**填记录号 + 现象（只写看到什么，不写归因） |

> 为什么不是"整份空 / 整份满"：空白文档的价值是**能看出哪些没验**。一旦 QA 填了第一条，其余项若没有独立状态，就会在"这份文档已经有内容了"的印象下被当成也验过了。

## 2 填写规则

1. **只写观察到的**，不写推断的。区分句式："窗口标题显示 X"（事实） / "attach 应该成功了"（推断，不写）。
2. **必须带时间戳**与构建标识（`build/MochiBox.app` 的产出时间或 commit）。
3. **失败也要记**，并且记下"当时屏幕上是什么"，而不是"我判断是哪里坏了"（后者属缺陷报告，不属本文）。
4. 一条记录只描述**一次连续操作**，不要合并多次尝试。
5. 截图放 `docs/assets/` 下（该目录已存在，不另建子目录），文件名 `manual-<YYYYMMDD-HHmmss>-<序号>.png`；本文用相对路径 `assets/<文件名>` 引用。
6. **不要在本文里判 PASS/FAIL 的口径**。是否通过由断言规则 + PRD 判定（见 R6：口径变更只能走 PRD）。本文只提供"看到什么"。

## 5 为什么单独成文（给后来者）

本轮曾出现一类问题：**文档里混入"运行事实"后，规则会带上"当时如此"的时效性**；反之，事实文档混入规则后，读者会分不清"这是要求还是观察"。

两者混写的典型后果：一处 GUI 观察被当成通用要求引用，或一条规则被当成"某次运行已验证"的证据。分开后：

- 要判断"**应该**怎样" → 读 `docs/prd.md`（需求）与 `docs/acceptance-assertion-rules.md`（断言怎么写）；
- 要判断"**当时**怎样" → 读本文；
- 要判断"**怎么实现**" → 读 `docs/architecture.md`。
