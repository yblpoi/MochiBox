## R1 断言三问（落笔前逐问）

| # | 问 | 漏了这一问会怎样 |
|---|---|---|
| ① | **错误实现能通过吗？**（能否被证伪） | 断言形同虚设 |
| ② | **正确实现能通过吗？**（有无假阳性） | 会把正确行为"修坏" |
| ③ | **有阳性对照吗？**（不只验"不该发生"） | **沉默的实现最容易全绿** |
| ④ | **失败时能定位到哪一环坏吗？** | 判对了但没人知道怎么修，修复要从入口重查整条链路 |

**共同点**：四问问的都是**断言自己会不会出错**，不是"覆盖了没有"。覆盖讨论被测对象；四问讨论断言本身。

**④ 的操作化**：若一条断言失败时无法判断是哪一环坏（例："`cache` 条目数不新增"失败 → 分不清是跳过没跑还是缓存写入没判），就拆成两条更靠近故障点的断言。

**真实实例**
- ② 失守：以"译文 == 原文"判"假译文" → 误伤 `OK` / `BGM` / `HP` 等**恒等翻译**（合法后端返回），正确实现被判失败，且可能诱导工程去"修好"正确行为。
- ③ 失守：`P0-09` 原先只有"不该请求后端/不该写缓存"这类阴性断言，**一个什么都不做的实现可全绿**；后补 `\C[2]350` 必须 `skipped` 这条阳性对照。
- ① 失守（易被误归类为"覆盖不全"）：只查 `cache.jsonl` 文件条数，而运行时缓存是内存 + 异步落盘 → **"写进内存但没落盘"的错误实现能通过**。

> 归类提醒：**覆盖不全是"少测了"，①②失守是"测错了"**。前者补一条即可；后者必须**先撤断言再重写**——补再多条也救不回一条不可证伪或会误伤的断言。

## R2 扫描"只有阴性断言"时，以**能力**为单位，不以**条目**为单位

按"这一行文字里有没有正向描述"扫描，会把**邻近条目的阳性断言**漏算成缺口，于是重复补一条与已有断言语义重叠的新条款 → 两份说法略有差异 → 又变成"两处标准互斥"。

**正确做法**：问"**这个能力**有没有被任何一条阳性断言覆盖"，而不是"**这一条**里有没有阳性断言"。

**真实实例**：`U+001F` 段数校验（`§5.4`）本行确实只有阴性断言，但 `P0-09` 已有"转义码位置不变"这条阳性断言。按条目扫会误判为"全阴性"。

**为什么容易误判**：阳性断言常常落在**另一个模块的验收行**里 —— `U+001F` 的**阴性**在解析侧（`§5.4`），**阳性**在 Agent 侧（`P0-09`）。按条目扫时，两个模块之间的字面距离被当成了"覆盖缺口"。这不是"读者不够小心"，而是**扫描单位选错了**。

## R3 枚举样本时，先分"成功组 / 失败组"，再分别写断言

把正确路径混进失败判据，是假阳性最常见的来源。

**真实实例**
- 把 `200` 与 `401` / `429` / `非 JSON` 并列，统一要求"返回错误码" → **`200` 是成功**，正确实现必失败。
- 把 `passthrough` 的"译文 = 原文"与"假译文"并列禁止 → `passthrough` 本来就要求译文等于原文（`P0-11`），必然误伤。
- 列举样本数与 code 数对不上（5 个样本对 3 个 code），逼着实现去"凑数"。

**操作形式**：样本列表先标注 `成功 / 失败` 两栏，再分别写断言；**成功组的断言必须包含阳性项**（有译文、写了缓存、状态为 `translated`）。

## R4 原因 ≠ 结果

凡写"某集合里有这几个成员"，先问：**这个集合是按结果分类，还是按原因分类？**

| 分类方式 | 能否用于推断结果属性 |
|---|---|
| 按**结果**（成功 / 失败） | 可以直接枚举，但**每个成员都必须有对应断言** |
| 按**原因**（`code` / error kind / 文本内容） | **不得**用于推断结果属性（`retryable`、是否告警、是否算脏数据、是否展示），**必须回到条件上判** |

**真实实例（同类错误已出现 4 次）**
1. 用 `code` 推 `retryable`：`bad_response` 在 `httpStatus=500` 时为 `true`、在 `400 + 非 JSON` 时为 `false`，同一个 code 答案相反。
2. 用"内容相等"推"假译文"：恒等翻译合法，内容相等不能作为判据；正确判据是**问来源**——取条目 `text` 跑同一个跳过判据，非 nil 才是脏条目。
3. 把 `200` 划进"要返回错误码"的集合（同 R3）。
4. 把 `circuit_open` 划进 `retryable = true`：熔断期请求根本不发出，**立即**重试必失败 → 必须 `false`；"出路"由自动半开提供，不由布尔值暗示。

## R5 定义贴在列表末尾，新增成员必须回引定义

这 4 次实例的共同成因**不是"不懂定义"，也不是态度问题**，而是：

> 它是在**补全列表时语义漂移**（定义在第 1 行，加到第 5 个成员时已切到"补全模式"，按"直觉上像不像"补，不再回看定义）。

因此对策不是"要更小心"——**"要更小心"不是可执行规则**。可执行形式是：

1. 凡枚举列表（`code` / 样本 / 字段取值），**定义必须同时写在列表头与列表尾**；或每个成员后附 `→ 依据：<定义原文>`；
2. **新增成员时必须回引定义一次**，不得只凭"它也是错误""它也是样本"归类。

只写"定义放末尾"解决的是**读**；"新增成员回引定义"才是把**写**的动作也变成检查点。

> 本节措辞由主理人指定保留：**"补全列表时语义漂移"**，不得改写为"要更小心"或"态度要严谨"。前者是可机械防御的流程缺陷，后者是道德要求——**道德要求无法写进检查表**。

## R6 口径的唯一变更通道是 PRD，QA / 工程无权自行放宽或收紧

| 角色 | 可以 | 不可以 |
|---|---|---|
| QA | 报缺陷、要求澄清、指出"该条不可验" | **自行豁免或降低断言强度**（"实现看起来合理，这条先不算"）；**自行加严**（文档外增标准） |
| 工程 | 指出断言与实现冲突、提供反例 | 以"实现更合理"为由跳过断言；在 selftest 里绕过缺陷 |
| PM | 修改 PRD 并留痕（版本 + 修订记录） | 口头改口径、只在消息里改口径 |

**遇到"实现看起来对、断言判它错"时**：不要当场判定谁对，报到 PM 做三选一——**转工程（实现没做到）/ 改标准（需求不可验）/ 补代理指标后转工程**。

**真实实例（**正面示例**，不是反例）**：`circuit_open` 的 `retryable` 曾有一版**提案**置 `true`（理由："否则用户以为没出路"）。**提案方没有自行定案，而是提交 PM 裁决**；PM 判 `false`，并把"出路"要求落到 `P0-13` 的 UI 断言上（倒计时 + 自动半开）。

**这段流程本身就是 R6 要示范的做法**：有争议时上报，而不是各自解释口径。记录时须区分"提交裁决"与"自行放宽"——**前者是规则生效，后者是规则失效**，两者性质相反，不可混写。

## R7 名称即语义：接口 / 字段 / 参数命名不得与语义相反

参数名、字段名是文档里**作用最强的注释**——比正文更可信，因为它看起来是**事实**：调用方手里确实有个叫 `raw` 的变量，传进去顺理成章。

**命名反了，读者会"照文档正确实现"却出错，而且不会怀疑。**

**检查形式**：对每个参数名问一句——**"传进来的东西，字面意思和真实语义一致吗？"** 若语义是"剥码归一后的文本"，就不得叫 `raw`；若语义是"缓存条目的哈希键"，就不得叫 `text`。

**真实实例**：`SkipRules.skipReason(for raw:)` —— 语义要求传**剥码并归一后的 `text`**，参数却叫 `raw`。照签名写 `skipReason(for: payload.raw)` 是"照文档正确实现"，但必然漏判 `\C[2]350`（`^\d+$` 匹配不上带前缀的串），与 `P0-09` 断言直接冲突。已改为 `for normalizedText:` 并在注释中写清正反配对。

**为什么单列一条**：其余失效是"读者**会发现问题**"；这一类是"读者**放心地做错**"。**检查成本不对称**——前者靠复核可救，后者一旦命名落地，所有人都会照着错的名字写下去。因此必须在**命名时**拦，而不是在复核时拦。

**检查形式（两个问题，缺一不可）**

> 每新增一个参数 / 字段，问两句：
> ① **名字的字面意思和真实语义一致吗？**
> ② **会不会让人把 A 传成 B？**
>
> 第 ② 问专门拦"**互补对**"——`raw`/`text`、`translatedText`/`translatedRaw`、`mapKey`/`cacheKey`、`order`/`seq`、`hits`/`hitCount`。**成对出现的名字最危险，因为两个都"听起来合理"。**

**命名自检清单**（"真实语义"由架构侧逐条核对并标注出处；"误用后果"由架构侧给技术后果 + PM 补玩家可感知后果）：

| 名字 | 真实语义 | 若被误用会怎样 |
|---|---|---|
| `raw` | 完整原始串，**含转义码**（`\C[2]350` 的整串）；用于回填重建与日志对账 | 当跳过判定输入 → `\C[2]350` 匹配不上 `^\d+$`，被送翻 + 写缓存；当缓存键输入 → 同句加不加转义码变成两个 key |
| `text`（`Segment` 的 text 段） | `splitSegments` 剥掉 code 段后的**自然语言片段**；跳过判定与 `mapKey` 的作用对象 | 拿 `raw` 顶替 → 见上；把 code 段并进来 → 送翻 `\C[2]`，回填后**玩家会看到控制码当正文显示** |
| `normalizedText` | text 段经 **NFKC + 空白折叠 + trim**（`normalizeForKey`）后的结果；`SkipRules.skipReason` 的唯一合法入参 | 传未归一的 text → `３５０`、`"350 "` 漏判（多发请求 + 写脏缓存） |
| `segments`（`[Segment]`） | **有序**段数组（code/text 交替），保存"哪个 text 段在哪个 code 段之后"，是回填的唯一依据 | 只传 text 段给重组 → code 段丢失，颜色/字号失效；乱序 → 转义码位置错 |
| `mapKey` | **页面侧键**：`joinForBackend(segments)` 的结果——`text` 段以 `U+001F` 连接，**纯字符串、无哈希**，由 Agent 计算，用于页内 `Map` 查找。**按契约 Agent 不做归一**（不 NFKC、不折叠空白、不 trim）——归一发生在 Host 算 `cacheKey` 一侧 | 用 `raw`（而非 `text`）算 → 同句带不同 `\C[x]` 前缀即**分裂成多个 key**（**这是 `mapKey` 侧唯一的成因**）。**归一化属 `cacheKey` 侧**：Host 若漏 NFKC / 空白折叠 → 全角、首尾空白会让同一句在缓存里分裂成两条（`mapKey` 不管这件事，它按契约不归一）。当持久化键 → 跨会话/跨语言对不复用；以为是 sha256 → 与 `cacheKey` 永远对不上。**与 `cacheKey` 互换 → 在各自命名空间内表现为「全 miss」且不告警**（用户只感觉"一直在重复花钱"）；若两者被混存进同一个字典，才可能出现交错命中——因此实现上不得共用一个容器 |
| `cacheKey` | **持久化键**：`lowerHex(SHA256("mvmz\|ja\|zh-Hans\|" + mapKey))`，**Host 唯一权威**，写 `cache.jsonl`、跨会话与跨语言对复用。**与 `mapKey` 不是同一种东西的两个名字，是两个不同层的键** | Agent 侧自行计算 → 两端不一致；Host 采信信封里的 `key` → 脏键落盘 |
| 信封 / `TranslationPushItem` 的 `key` | 单值键，语义 = **`mapKey`**（页面侧键，**不是 `cacheKey`**）；由 Agent 计算，Host 收到后**一律丢弃并重算** | 当 `cacheKey` 直接落盘 → 脏键入库；Agent 查页内 `Map` 时传成 `cacheKey` → 查不到，**永命中不了**；把 `cacheKey` 塞进此字段 → 表现为文本流出现哈希串（比"当原文展示"更严重：会污染缓存） |
| `translatedText` | 后端返回译文的**原文形态**，段间 `U+001F` 连接，**未重组**；是重组的输入 | 当作可直接绘制的最终串 → **屏上出现 `U+001F`**，或丢 code 段 |
| `translatedRaw` | **重组之后**的完整串（code 段已按原位插回），可直接绘制 | 与 `translatedText` 互换 → 段数校验失败 → 整条判 `segment_mismatch` **丢弃（全量丢译）**。**这两名字的直觉与实际正好相反，是本清单最危险的一对** |
| `surface` | 原始类名（`Window_Message` / `Window_Base` / `Bitmap`） | 当分类用 → UI 分组失效；反过来由 `surfaceKind` 还原 → 多对一，不可逆 |
| `surfaceKind` | 派生分类 `dialogue` / `menu` / `system`（可选，P0 只写不读） | 用它替代 `surface` 存库 → 丢原始类名（P1-06 分类导出需要它） |
| `order` | 会话内文本事件序号，**从 1 开始**、单调（可选，P0 只写不读） | 纳入 `cacheKey` → 同句永不复用；当缓存行号用 → 与 `seq` 混淆 |
| `occurrences` | 同一 `mapKey` 在当前文本流中的**累计出现次数** | 当"已渲染行数" → 统计错；当本帧计数 → 去重逻辑错 |
| `seq` | **`cache.jsonl` 行序号**（追加写，重放时最大者胜） | 与 `order` 混 → compaction / 淘汰判错；当事件序号 → 日志对账错 |
| `hitCount` | **单个缓存条目**的命中累计（增量行） | 与 `StreamStats.hits` 混 → 命中率算错（分母 = `hits + newTranslations`，**不含 skipped**） |
| `srcLang` / `tgtLang` | BCP-47，V0.1 固定 `ja` / `zh-Hans`；**禁 `fromLang` / `toLang` 别名** | 引入别名 → 解码两份契约；改成 `zh-CN` → 缓存分片名与 key 公式全变（需迁移） |
| `engineFamily` | 分段 / 键公式的族别（`mvmz`），**不是** `engine`（识别结果 `MV`/`MZ`/`unknown`） | 传 `MV`/`MZ` → `cacheKey` 公式前缀变化 → **已有缓存全部失效** |
| `sessionToken` | 16 hex，每会话新生成，**仅用于信封串话校验**（不匹配即丢弃 + 计数） | 持久化复用 → 跨会话消息被接受；当认证凭据 → 语义不符（它不防伪） |
| `detail` | `ErrorInfo` 的**成因细分**，非枚举、工程可自由调整；QA 只断言 `code` | 拿 `detail` 写断言 → 随实现改动而红；为其新增 `code` → 违反"一个 code 一个语义" |
| `httpStatus` | 失败响应状态码，是 `retryable` 的判定输入（`bad_response` 按 `>= 500` 分） | 不看它、按 code 静态判 `retryable` → 5xx 不重试 |
| `maxMapSize`（默认 20000）vs `maxCacheEntries` | 前者是**页内 Map 上限**，后者是**磁盘缓存条目上限** | 互换 → 内存爆或磁盘无限增长；用前者当缓存上限 → 淘汰策略错位 |

**两条使用说明**

1. **语义以架构侧为准**："真实语义"列由架构逐条核对架构正文并标注出处。若本表与 PRD 表述不一致，**以源码为准并回改本表**。
2. **`translated` / `translatedRaw` 在 PRD 里是两个名字、同一个概念**：`TextEvent.translated`（§5.2）与 `HostCommand.translatedRaw`（§5.3）都指"重组后可直接绘制的串"，而 `TranslateResult.translatedText`（§5.4）是"未重组的 `U+001F` 形态"。**PRD 当前冻结，本轮不改**；已记入 v0.3.5 待办（统一为一名的方案见待办）。**在改之前：实现按架构命名，读 PRD 时须做此映射，不得据 PRD 的两个名字推断成两种数据。**

## R8 优先级列表里存在包含关系时，精确项优先，且不得靠行序表达

凡写"按顺序匹配"的列表（引擎识别、跳过规则、错误码优先级、后端选择），先检查成员之间**是否存在包含 / 重叠关系**（`Scene.pck` ⊂ `*.pck`、`400+非 JSON` ⊂ `bad_response`）。

若存在：
- **更具体的必须优先命中**；
- **不得依赖列表顺序**表达这层含义——行序只用于"彼此无关的特征"之间。

**理由**：靠行序表达包含关系时，**任何一次调序都会静默改变判定结果**，而结果又会被缓存、验收用例和用户数据继承。调序的人通常以为自己在整理文档。

**真实实例**：`§A.1` 原规则 12 为 `godot: project.godot；或根下 *.pck`，规则 13 为 `siglus: Scene.pck`。`Scene.pck` 匹配 `*.pck`，且 12 在前 → Siglus 游戏被识别为 `godot` + `signature_conflict`。**实现逐字执行 §A.1，没有错；错在需求把通配写在精确名之前。**

**与 R5 的区别**：R5 管"写定义时不回看"，本节管"列表结构本身让泛化项赢"——**前者是人的问题，后者是结构的问题**。结构问题无法靠更小心解决，只能改结构。

## R9 技术依据必须可复现：不得用"听起来合理的内置行为"解释未验证的失败模式

凡在需求/设计里写下"**不得用 X，因为 X 会 Y**"，**Y 必须可复现**——给一行验证代码或一段实测输出。没有实测依据的机制解释，不得作为禁令理由。

**为什么**：禁令的正确性依附于理由的正确性。**理由一旦被证伪，整条禁令会被一起怀疑**——而原本该保留的是禁令，该换的只是理由。

**真实实例（第 10 例）**：曾以"`CharacterSet.whitespaces` 会连 `U+001F` 一起吃掉"作为禁令依据。实测：

```
whitespaces.contains(U+001F)            = false
whitespacesAndNewlines.contains(U+001F) = false
components(separatedBy: .whitespaces).count = 1        // "甲\u{1F}乙"
U+001F survived = true
```

**机制不成立**。真实风险是另外两条：① 这些集合的覆盖范围**随平台/引擎而变**（U+3000、NBSP、行分隔符是否计入不一致）→ 同一句在不同系统算出不同键；② 若被替换成含 C0 控制字符的集合（`.controlCharacters`），届时才真的会吃掉分隔符。

**禁令保留、理由替换**——这才是正确处理；错误做法有两种：因为理由错了就删掉禁令（丢掉真实风险），或因为禁令对就保留错误理由（等下一次被证伪）。

**更优写法：三件套替代单条禁令**

| 件 | 作用 | 例（`§5.1` 归一） |
|---|---|---|
| **不变量**（可观察结果） | 定义"正确必须满足什么" | `count(U+001F) == 段数 − 1`；且切分后逐段剥白，**段内容序列**与归一前一致 |
| **禁止项** | 拦住已知的错法 | 禁止 `.whitespaces` / `\s` 等平台相关集合 |
| **依据** | 让禁令可被验证、可被反驳 | **规范**：`U+001F` 属 Cc；`.whitespaces` = Zs + U+0009，不含 Cc |

只写"禁止项"时，下一个人换个等价写法（`.controlCharacters`、自写正则）就绕过去了；**不变量才拦得住换写法**。

> **注意"依据"一栏写的是规范而非实测**：`U+001F` 属 Cc 是类别定义，恒成立；写成"实测 `contains == false`"会把规范事实降级为经验事实——经验事实会被下一次实验推翻，规范事实不会。**任何实测若与规范不符，先怀疑实现。**

**第二句：断言必须自带"一进一出"例子。**

凡不变量 / 断言，必须同时给出 `输入 → 期望输出`（或 `输入 A` 与 `输入 B` → 同 key / 不同 key）。**没有例子的视为未定义**——不是"以后补"：未定义的断言会被实现方按各自理解填，然后变成两处标准。

**同一族错误的第三次（三次都靠对方举反例才拦住，无一次自检拦住）**：

| 提出者 | 断言 / 理由 | 错因 |
|---|---|---|
| 主理人 | "`CharacterSet.whitespaces` 会吃掉 `U+001F`" | 用一个听起来合理的内置集合解释未验证的失败模式 |
| PM | "`translatedRaw == raw` 即假译文" | 用一个好验的代理指标当判据 |
| 架构师 | "`U+001F` 的位置序列不变" | 把"分隔符没被动过"与"字符串长度没变"混为一事 |

**第三个反例证明这条的必要性**：`text = ["甲  ", "乙"]` → join `甲␟乙`（`␟` 下标 3）→ 折叠空白 → `甲 ␟乙`（`␟` 下标 2）。**正确实现下"位置不变"必然为假**——写出这条例子，5 秒就能发现断言是错的；不写，就要等 QA 报"正确实现失败"再返工。

**与 R9 的关系**：R9 约束"**理由**必须可复现"，本句约束"**断言**必须自证"。两面同一件事：**不要让没有例子/没有验证的说法进入文档**。

**与 R7 的区别**：R7 管"**名字**与语义不符"；R9 管"**理由**与事实不符"；本句管"**断言**没有可判定的例子"。三者都是"读者相信了不该相信的东西"——信名字、信解释、信一句无从验证的断言。

## 10 与 `manual-acceptance.md` 的分工

| 文档 | 内容 | 时效 |
|---|---|---|
| **本文** | 怎么写断言（规则） | 跨轮有效 |
| `docs/manual-acceptance.md` | 某次运行的事实（窗口状态、点了什么、看到什么） | 一次性，随运行产生 |

**禁止事项**：不得把规则写进 manual-acceptance（会让事实文档变成半规则文档）；不得把某次运行的观察写进本文（会让规则带上"当时如此"的时效性）。

## 12 文档结构自检（三条一体，缺一即漏）

**适用对象**：PRD 里所有表格（需求池、数据契约字段表、优先级表、元信息表）。**时机**：每次写完或改完表格必跑同一段脚本，不靠肉眼、不靠渲染预览。

| # | 检查 | 观测量 | 漏了会怎样 |
|---|---|---|---|
| ① | 每行列数一致（**未转义**竖线数相同） | 列数 | 单元格内**裸竖线**（如 `ps -ax \| grep`）把该行多切一列 |
| ② | 表内**无空档**（首条到末条数据行之间，每行都以 `\|` 开头） | **连续性** | 单元格内**裸换行** → 片段掉出表外，**整表被切成多段**，渲染成多个残表 |
| ③ | 首块长度 ≥ 3 且第 2 行是分隔行 | **块完整性** | 表头行缺闭合竖线 → 后续行脱离表体成孤行（本次 #11 就是这种） |

**为什么必须是三条**：②③ 的损坏**不改变列数**——表被切成三段时，**每段每一行仍有正确的竖线数**，`①` 照样全绿。**选了错的观测量，检查照样通过**：本次真实故障就是在"0 处列数异常"的绿灯下、带着三张残表交付的。

**判定口径（一句话）**：**列数正常 ≠ 表没被切断。切断的观测量是连续性，不是列数。**

**可复现结果（`docs/prd.md`，2026-10-23 复算）**：全文 **753 行**；表格 **26 块**，块长 `10,5,5,22,7,12,11,9,13,6,8,4,25,6,7,8,8,6,8,11,23,3,7,16,8,7`；**残表 0**、**块内列数不一致 0**、`P0` 表 **20 条**数据行位于 136–155、**空档 0**。

**自检脚本的核心两句**（其余为读数）：

```python
def nc(l): return l.count('|') - len(re.findall(r'\\\|', l))     # 未转义竖线数
gaps = [i for i in range(rows[0], rows[-1]+1) if not lines[i-1].startswith('|')]  # ② 连续性
```

> **与 R1-③ 是同一族**：R1-③ 问"阳性对照会不会被执行"，本节问"检查跑了但有没有对着目标"。两者都是**检查存在、方向错了**——比"没检查"更难发现，因为绿灯是真的。
